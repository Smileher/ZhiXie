> 用途：路演答辩环节的准备稿（不进 PPT）

## 一、产品差异与必要性

**Q1. 和手机自带提醒有什么区别？为什么要在电脑上再装一个？**

结论：动作不同、约束力不同、创建成本不同。
- 依据：手机提醒的落点是"看一眼手机"，这本身就是打断后的新干扰；知歇的落点是**桌面全屏弹窗 + 可附加锁屏 / 关机 / 重启**，形成真正的离开屏幕的约束力；
- 补充：创建方式上，手机提醒仍需手动选时间与重复规则，知歇支持一句话生成；且知歇数据全部在本机、无需账号。

**Q2. 电脑系统自带的日历提醒也能定时，为什么需要知歇？**

- 系统日历偏向"事件管理"，需要用户自己理解重复规则；
- 知歇的核心是**降低创建成本**（自然语言）+ **提升提醒的存在感**（全屏弹窗、视觉可定制）+ **可执行系统操作**；
- 系统日历无法把"锁屏睡觉"这类系统动作作为提醒的一部分。

**Q3. 和番茄钟类工具比，你们的优势是什么？**

- 番茄钟本质是固定节奏（通常 25 分钟），知歇的间隔与文案都可自由调整，且支持"到点强制离开屏幕"；
- 番茄钟多数不含系统操作能力；知歇可锁屏 / 关机 / 重启，并提供 60 秒可撤销倒计时；
- 番茄钟多数需要注册账号，知歇零账号、数据全本地。

**Q4. 这个产品会不会就是"提醒 + AI"，同质化很严重？**

- 提醒功能确实是成熟品类，**本作品的差异化在交互层的重构与工程上的可靠性设计**；
- 具体体现：一句话创建、双通道离线兜底、校验优先落库、弹窗视觉可定制、学生场景预设；
- 本赛道（AIGC 创新组）关注的是"智能体在各功能模块中的作用"，知歇把智能体同时用于**规则生成、休息建议、弹窗文案**三处，而非只在对话框里。

## 二、智能体与 AI 相关

**Q5. 大模型输出的可靠性怎么保证？万一它编造一个不存在的提醒怎么办？**

结论：**大模型的输出不直接落库，必须通过白名单校验层。**
- 依据：`validate_draft` 对五个字段统一校验——类型（仅四种合法值）、时间（合法 `HH:MM`）、星期（0–6）、日期（1–31）、系统操作（仅锁屏/关机/重启），非法值过滤或回落默认值；
- 佐证：单元测试 `cloud_drafts_are_validated` 故意构造"非法类型 + 非法时间 + 越界星期 + 越界日期 + 非法系统操作"的脏数据，验证全部被正确处理；
- 补充：解析结果以表单可视化呈现，**用户确认后才写入**，人始终在最终决策位。

**Q6. 为什么要做本机规则引擎？直接用大模型不是更好吗？**

- 三个理由：**可用性**（未配置密钥或断网时功能不能断）、**成本**（不产生 API 费用）、**隐私**（默认不联网）；
- 本机引擎面向高频中文表达做了针对性覆盖，日常使用场景下命中率足够；
- 云端是"可选增强"，不是"必要依赖"。

**Q7. 本机规则引擎能覆盖多少表达？边角情况怎么办？**

- 覆盖五类：中文数字时间、相对时间、连写周几、日期词、系统操作词；
- 无关键词时会回落为"单次提醒"并保留用户原句作为标题（测试 `local_parser_falls_back_to_once_without_keywords`），**不会报错也不会丢输入**；
- 已知限制：英文时间表达（如 "at 3 pm"）覆盖有限，开启云端后可完整支持——这一点我们在测试报告的"已知限制"里主动写明了。

**Q8. 这是用了低代码平台搭的吗？"低代码 / 无代码"体现在哪？**

- 产品本身是原生桌面应用，不是低代码平台生成的；
- **低代码体现在智能体的编排与使用方式上**：普通用户零配置即用；进阶用户只需填三格表单（接口地址、模型名、密钥）就完成接入，**全程不写一行代码**；解析结果可视化确认、弹窗视觉可视化调校；
- 我们理解赛道强调的是"用户侧无需编码即可完成智能体的接入与编排"，这三点正好对应。

**Q9. 如果接入其他大模型（非 DeepSeek）能行吗？**

- 接口按 OpenAI 兼容格式实现，地址与模型名都可自由修改，理论上任何提供 OpenAI 兼容对话补全接口的服务都可接入；
- 默认值填 DeepSeek 只是"开箱可用"的便利设置。

**Q10. 大模型返回的 JSON 格式不规整怎么办？**

- 有一层容错：返回内容被 ``` 代码块包裹、或前后夹杂解释性文字时，仍能提取出 JSON 对象（测试 `json_extraction_tolerates_code_fences`）；
- 若完全无法解析，则按失败处理并回落本机引擎。

**Q11. 智能体的提示词是怎么写的？会不会被用户输入误导？**

- 提示词明确约束输出为规定字段的 JSON，`temperature` 设为 0.2 以降低随机性，并有 40 秒超时；
- 即便模型被误导输出异常字段，也会被校验层拦截——**校验层是最后一道防线，不依赖模型自觉**。

## 三、技术实现与工程质量

**Q12. 为什么选 Tauri 而不是 Electron？**

- 体积与资源占用：Tauri 使用系统原生 WebView，不打包 Chromium，安装包与内存占用低一个量级；
- 关键能力（窗口、托盘、系统操作、自启动）由 Rust 侧实现，性能与可控性更好；
- 代价是平台差异需要分别处理，我们通过双平台真机验证 + 自动化测试覆盖。

**Q13. 你说有 138 项测试，测的都是什么？**

- 前端 77 项：休息节律调度（38）、弹窗状态机（30）、桌面策略（5）、默认值（2）、视图与设置（2）；
- Rust 61 项：智能体解析与校验、数据原子写入与版本升级、导入校验、调度与提醒、系统命令执行结果；
- 测试关注的是**容易出错的时序与状态问题**：延迟到达的旧触发不能覆盖新触发、Escape 关闭不重复隐藏、失败的关机保留弹窗可重试、导入后残留倒计时被清除等。

**Q14. 数据会不会损坏或丢失？**

- 数据采用**原子写入**：先写临时文件，成功后再替换目标文件，写入中断不会破坏原文件；失败时清理残留临时文件；
- 数据文件带版本号（当前为 6），版本不匹配时**先备份旧文件再重建默认值**，不静默丢弃；
- 提供导出 / 导入 JSON 备份，用户可自行迁移与恢复。

**Q15. 关机 / 重启这种危险操作，出错了怎么办？**

- 触发后进入 **60 秒可撤销倒计时**，用户可随时取消；
- 系统命令执行失败时，弹窗保留并提供重试，不会静默丢弃；
- 系统命令的退出码与超时都有处理（测试 `system_command_reports_nonzero_exit_and_timeout`）。

**Q16. macOS 上弹窗透明用到了私有 API，合规吗？**

- 使用的是 Tauri 的 `macos-private-api` 特性，本作品通过 DMG 直接分发、**不上架 Mac App Store**，符合平台授权要求；这一点我们在技术文档中已明确说明。

**Q17. 代码是你自己写的吗？为什么说有"人机协同"的开发范式？**

- 项目由本人独立主导：需求定义、架构分层、数据结构、校验规则、测试用例设计都由本人完成；
- AIGC 工具作为辅助参与编码实现与文案打磨，所有产出都经过审阅与测试验证；
- 我们把这个过程本身当作一个创新点来呈现：**"AI 生成 + 人工架构设计 + 测试闭环"**，并用 138 项自动化测试作为可验证的闭环证据。

**Q18. 项目规模到底多大？**

- 自有代码约 8500 行：Rust 侧核心约 5400 行（`lib.rs` 3800 / `startup.rs` 819 / `agent.rs` 738 等），前端约 2800 行；
- Git 全程管理，一个功能一个提交，提交信息使用中文。

## 四、安全与隐私

**Q19. 会收集用户数据吗？**

- 不会。无遥测、无广告 SDK、不采集任何用户数据；
- 所有数据保存在本机应用配置目录。

**Q20. 启用云端后，我的哪些数据会被发出去？**

- **只有用户输入的那一句话**。不发送提醒列表、不发送设置、不发送设备信息；
- 密钥仅保存在本机 `agent-config.json`，不上传到我们或任何第三方。

**Q21. 密钥存在配置文件里安全吗？**

- 密钥不会出现在界面明文（输入框为密码型），也不随导出备份外泄；
- 这是本地单机工具的常规做法：数据不出本机、不经过我们服务器（我们也没有服务器）；
- 若用户使用共享电脑，可随时清空密钥或关闭云端开关。

**Q22. 有没有做安全加固？**

- 前端有 CSP 限制资源加载来源；
- 桌面环境下策略性屏蔽浏览器类快捷键与右键菜单，防止误操作（有专项测试 `browser-policy`）；
- 不提供任何网络监听端口，应用本体不对外开放服务。

## 五、推广、可持续性与商业化

**Q23. 学生群体真的会用吗？会不会装了不用？**

- 这类产品的关键不是"装"，而是"提醒是否被感知到"——我们用全屏弹窗 + 系统通知 + 个性化文案三重手段提高存在感；
- 预设的学生场景锚点（吃饭 / 下课 / 周末）让用户开箱就有可用的节奏，降低"从零配置"的心理门槛；
- 推广期我们在校内做试用反馈，用真实使用数据迭代文案模板。

**Q24. 后续如何推广？**

- 短期：校内机房 / 实训室试点，可统一施加休息节律并定制校风文案，零账号便于批量部署；
- 中期：面向备考与远程办公人群的垂直内容渠道；
- 长期：保持个人版免费，探索校园 / 机构批量定制（文案模板、统一策略下发）。

**Q25. 怎么盈利？**

- 个人版保持免费，不设功能墙；
- 潜在方向：面向学校 / 机房的定制版（统一策略、文案模板库、批量部署支持）；
- 我们刻意不做广告，这与产品"减少干扰"的定位冲突。

**Q26. 有没有考虑过做成手机端 / 网页版？**

- 本产品的核心价值依赖**桌面系统能力**：全屏弹窗、锁屏、关机、开机自启，这些在网页端无法实现；
- 手机端可作为提醒同步的补充，但不是当前方向——先把桌面体验做扎实。

**Q27. 为什么不用低代码平台直接搭？**

- **桌面系统能力超出低代码平台的能力边界**：全屏透明弹窗、锁屏 / 关机、开机自启、托盘常驻，这些低代码平台都做不到；
- 低代码思路体现在智能体的接入与编排上（三格表单即完成接入，无代码），而不是用来搭建应用本体。

## 七、可能的追问（刁钻题）

**Q32. 你这个"校验层"听起来很简单，凭什么算创新点？**

- 单看实现确实不复杂，但它是**有意识的设计选择**：把 AI 的不确定性挡在数据写入之前；
- 很多 AI 应用的通病是"直接把模型输出当结果"，出了问题无法定位；我们的做法是让模型只负责"提出建议"，系统负责"判断是否可执行"；
- 并且这个设计有对应的测试用例作为证据，不是口头承诺。

**Q33. 如果大模型能力越来越强，你这个本机规则引擎不就没用了？**

- 恰恰相反，本机引擎解决的是**非模型能力问题**：断网、未配置、成本、隐私；这些约束不会因为模型变强而消失；
- 而且本机引擎还提供了**兜底确定性**——模型不可用时产品仍然可用。

**Q34. 有没有真实用户数据支撑？**

- 原型目前已在本人与同学中进行了功能走查（14 项手工用例全部通过）；
- **量化问卷调研正在校内推进**，调研方案与问卷题目已定稿（见 06 号文件），数据回收后会据实补充；
- 我们不会在没有数据支撑的情况下编造使用量或满意度数字。

**Q35. 演示时如果网络出问题怎么办？**

- 断网恰好是本产品的演示分支：会明确提示"云端不可用，已自动切换本机规则引擎"，功能不中断；
- 同时我们准备了离线录屏作为备用。

## 八、答辩技巧备忘
